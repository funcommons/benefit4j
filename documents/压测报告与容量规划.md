# benefit4j 压测报告与容量规划

> **版本** v1.2.6 · **更新** 2026-08-22 · **状态** 已发布 · **维护** benefit4j 团队
> 以代码现状为准。压测环境:本地单实例(Mac 8核,JDK17,PG17,Redis7)。

## 1. 压测目标

补齐可观测性 P0 缺口(压测/容量),给 benefit4j runtime 查询接口建立 QPS/P99 基线 + 容量规划依据。

- **被压接口**:`GET /benefit/api/v1/runtime/users/{userid}/assets`(用户资产查询,走 DB + 签名校验)
- **工具**:Python 标准库(urllib + hmac/hashlib,多线程),脚本 `backend/benefit4j-it/scripts/bench_consume.py`
- **场景**:签名鉴权 + DB 查询(assets),代表 runtime 读路径

## 2. 压测结果

### 2.1 限流生效(生产配置,scope=APP 300/分)

| VU | 时长 | 总请求 | QPS | 200 | 429 | P99 RT |
|---|---|---|---|---|---|---|
| 20 | 10s | 35198 | 3520 | 300 | 34898 | 11.8ms |
| 50 | 10s | 35600 | 3560 | 0 | 35600 | 28.0ms |

**结论**:限流严格生效(单 App 300/分=5 QPS,超限全 429)。429 快速返回(~5-10ms)不耗 DB。**限流是生产第一道护盾**。

### 2.2 真实容量(临时关限流)

| VU | 时长 | 总请求 | QPS | 200 | avg RT | P50 | P95 | P99 | max |
|---|---|---|---|---|---|---|---|---|---|
| 50 | 10s | 21468 | **2147** | 21468 | 22.2ms | 21.2ms | 35.6ms | **46.4ms** | 78ms |
| 100 | 10s | 23673 | **2367** | 23673 | 40.3ms | 37.8ms | 70.9ms | **97.9ms** | 301ms |

**关键发现**:
- 50→100 VU 并发翻倍,QPS 仅 2147→2367(+10%),RT 翻倍(22→40ms)→ **50 VU 后接近单实例瓶颈**
- 100 VU P99 97.9ms(仍 <100ms),max 301ms(长尾,GC/锁竞争)
- 全 200(无错误,签名+DB 稳定)

## 3. 容量规划

### 3.1 单实例容量基线(本地 Mac,非生产硬件)

| 指标 | 值 | 说明 |
|---|---|---|
| 查询 QPS(无限流) | ~2200 | 50-100 VU 饱和点 |
| 查询 P99 | 46-98ms | 50/100 VU |
| 限流下单 App | 5 QPS(300/分) | 生产默认,可按租户调 |
| 单实例理论上限 | ~2500 QPS | RT >100ms 前的拐点 |

> 注:本地 Mac(8核)非生产 Xeon/EPYC,生产服务器单核更强 + JVM 调优,查询 QPS 预估 3000-5000(1.4-2 倍)。

### 3.2 机器规格 → 扣减 QPS(token 平台,写为瓶颈)

压测基线(本地 Mac 8 核,查询 ~2200 QPS)。生产 Xeon/EPYC 单核更强 + JVM 调优。**扣减写路径是瓶颈**(本地事务 + 跨桶乐观锁 + outbox,RT 约为查询 2-3 倍)。按"查询 QPS × 写读比系数 × 生产硬件系数"推算单实例扣减 QPS:

| 机器规格 | 单实例扣减 QPS | 单实例查询 QPS | 说明 |
|---|---|---|---|
| 4C8G | ~600 | ~1500 | 入门,小租户/PoC |
| **8C16G** | **~1000** | ~3000 | 主流,单实例生产基线 |
| 16C32G | ~1800 | ~5000 | 大规格,高密度 |

> 推算依据:本地 Mac 8 核查询 2200 QPS → 生产 8C16G 查询 ~3000(1.4×);扣减写 = 查询 × 0.33(乐观锁 + 事务 + outbox 开销) → ~1000 QPS。16C 按核数线性 ~1800。

### 3.3 集群 → 峰值 QPS → 支持用户量(DAU)

benefit4j 无状态(JWT + Redis nonce),集群线性扩展。**token 平台峰值模型**:日均调用 = DAU × 人均日调用次数;峰值 QPS = 日均调用 × 峰均比 ÷ 86400(峰均比取 8,即峰值是日均 8 倍,集中 3 小时高峰)。

**人均日调用频次(token 平台分级)**:
- 轻度(ToC 赠送/试用):50 次/天/用户
- 中度(企业 SaaS API):200 次/天/用户
- 重度(AI Agent/高并发集成):1000 次/天/用户

**支持 DAU 矩阵(8C16G × N 实例,中度 200 次/天)**:

| 实例数 | 集群扣减 QPS | 日均调用 | **支持 DAU(中度)** | 支持 DAU(轻度) | 支持 DAU(重度) |
|---|---|---|---|---|---|
| 1 | 1000 | 1.08M | **5400** | 21600 | 1080 |
| 2 | 2000 | 2.16M | **10800** | 43200 | 2160 |
| 4 | 4000 | 4.32M | **21600** | 86400 | 4320 |
| 8 | 8000 | 8.64M | **43200** | 172800 | 8640 |
| 16 | 16000 | 17.28M | **86400** | 345600 | 17280 |
| 32 | 32000 | 34.56M | **172800** | 691200 | 34560 |

> 公式:日均调用 = 峰值QPS × 86400 ÷ 8(峰均比 8);DAU = 日均调用 ÷ 人均日调用。

### 3.4 大厂场景对照(token 平台)

| 场景 | 目标 DAU | 调用频次 | 峰值 QPS | 推荐规格 | 实例数 |
|---|---|---|---|---|---|
| 创业期 token API | 1万 | 中 200/天 | ~200 | 8C16G | 1 |
| 成长期 SaaS | 10万 | 中 200/天 | ~2000 | 8C16G | 2-4 |
| **成熟期(中型 token 平台)** | **50万** | 中 200/天 | ~10000 | 8C16G | 10 |
| 大厂级(OpenAI/Anthropic 量级) | 500万 | 重 1000/天 | ~50000 | 16C32G | 28+ |
| 超大(阿里云 API 网关) | 5000万 | 重 1000/天 | ~500000 | 16C32G | 280+ + 分库分表 |

> 注:500万 DAU 以上需**分库分表**(ubma_consume 流水按 app_id 分片,PgBouncer + 读写分离)+ **Redis 集群**(nonce/限流/幂等)+ **MQ 异步化**(outbox → Kafka)。当前 PG 原生分区 + 单 Redis 是 50万 DAU 级的天花板。

### 3.5 多实例线性扩展预期

benefit4j 无状态(JWT + Redis nonce),可水平扩展:
- 2 实例 → ~2000 扣减 QPS
- 4 实例 → ~4000
- 瓶颈转移:PG(分区表 + 索引)、Redis(签名 nonce/限流/幂等)

### 3.6 扣减写路径(推算,未压测)

- postConsumesDirect 走本地事务 + 跨桶乐观锁,RT > 查询(多桶 update + consume insert + outbox insert)
- 预估单实例扣减 QPS ~1000(8C16G,乐观锁竞争 + 事务)
- **建议**:后续补写路径压测(需幂等键 + 数据防耗尽,独立环境)校准

### 3.7 瓶颈与优化建议

| 瓶颈点 | 现状 | 优化 |
|---|---|---|
| PG 查询 | ubma_consume 已分区 + 全局索引 | 桶查询(item/set)走 cache(已接 @CacheableGet) |
| Redis | 签名 nonce/限流/幂等单点 | 多实例共享 Redis,连接池调优;50万 DAU+ 转 Redis 集群 |
| 签名计算 | 每次 HMAC-SHA256 | 客户端缓存短时签名,或内网降级为 token-only |
| 长尾(max 301ms) | GC/锁竞争 | JVM 调优(G1/ZGC),Druid/连接池调优 |
| 扣减乐观锁 | 跨桶 update 串行 | 热点桶分片(按 userid 散列),或异步化(outbox) |

## 4. SLO 建议

| 接口 | SLO(P99) | 依据 |
|---|---|---|
| runtime 查询(assets) | <100ms | 100 VU P99 98ms |
| runtime 扣减(direct) | <200ms | 写路径推算(待压测) |

## 6. 压测脚本

`backend/benefit4j-it/scripts/bench_consume.py`:
```bash
python3 bench_consume.py <VU> <duration_sec>
# setup 自动: 平台登录 + 建 app + APP 登录
# 压测: getUserAssets (带 HMAC 签名)
# 输出: QPS / 状态码 / avg/P50/P95/P99/max RT
```

*压测环境为本地单实例(Mac 8核),数据量小(assets 查空)。生产容量需在真实硬件 + 数据量下校准;扣减 QPS 为推算,待写路径压测校准。*
